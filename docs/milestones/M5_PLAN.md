# M5 구현 계획 (v2) — PSBT 서명

상태: **구현 완료 (2026-11-21)** · 승인: 결정 1~5 모두 권장안 · 남은 것: Signet 실송금 확인 (사용자) · 근거: [SIGNING_SURVEY.md](../SIGNING_SURVEY.md) (8개 레퍼런스 서명 과정 전수조사)

## 0. v1에서 바뀐 점

v1은 기본적인 검증·서명이었다. v2는 조사에서 프로젝트마다 가장 강했던 부분을 모았다.

| 추가 | 가져온 곳 |
|---|---|
| "주장"과 "검증된 사실"을 **Rust 타입으로 분리** (재파생 없이는 검증된 값을 만들 수 없음) | SeedSigner의 원칙을 컴파일러가 강제하도록 강화 |
| 문제를 **공격 / 형식 오류 / 경고**로 나눠 화면과 다음 행동을 다르게 | SeedSigner |
| segwit v0 입력 금액: **이전 거래가 없으면 먼저 차단, 사용자가 명시적으로 해제할 때만 진행** | Passport Prime, Trezor(OneKey) |
| 전원이 켜져 있는 동안 **서명한 UTXO의 금액을 기억**, 다른 금액으로 다시 오면 차단 | Coldcard |
| 입력 스크립트 누락·불일치·불필요 검사, **전역 xpub 재파생 검증** | SeedSigner, Passport Prime |
| 승인 후 **서명 직전에 판정을 다시 계산**해 승인 때와 같은지 확인 | Coldcard, Trezor |
| SIGHASH는 **ALL(탭루트 DEFAULT)만** | Jade, Krux |
| 수수료 기본 차단선, 단계별 경고 | Coldcard |
| ECDSA **low-R 그라인딩**(Bitcoin Core와 같은 71바이트 서명) | Coldcard, Jade |
| **모든 서명을 직접 검증**, 키·nonce 즉시 소거 | Jade·Coldcard·Passport |
| 마지막 화면 기본 선택을 "취소"로 (실수로 서명 방지) | Passport의 밀어서 서명을 키보드에 맞게 |

## 1. 목표

지갑 앱이 만든 PSBT를 QR로 받아, **기기가 스스로 확인한 사실만** 사람에게 보여 주고, 모든 화면을 거친 뒤에만 서명해 QR로 돌려준다.

**완료 기준:** Signet에서 Sparrow → Bitpunk(시뮬레이터) → Sparrow 실제 송금 성공.

## 2. 범위

| 포함 | 나중 |
|---|---|
| PSBT v0 (BIP-174, 탭루트 필드 BIP-371) | PSBT v2 → M7 |
| 단일 서명 4종: P2WPKH, P2TR 키 경로, P2SH-P2WPKH, P2PKH | 멀티시그, 탭루트 스크립트 경로 → M7 |
| 서명 해시 3종: 레거시, BIP-143, BIP-341 | 메시지 서명 → M6 |
| ECDSA(RFC 6979, low-S, low-R), Schnorr(BIP-340), 서명 직후 검증 | TRNG 블라인딩·보조 난수 → 하드웨어 트랙 |
| 검증기(공격·오류·경고 분류), 검토·승인 화면 | 경고 강도·수수료 차단선 설정 화면 → M6 |
| 서명된 PSBT QR 출력 (축소본) | SD 저장·최종화 tx → M8 |

## 3. 신뢰 모델

- PSBT 안의 지문·파생 경로·xpub·스크립트는 모두 **호스트의 주장**이다. 표시할 수는 있지만 판단 근거로 쓰지 않는다.
- 판단은 **시드에서 직접 파생한 키로 스크립트를 다시 만들어 일치할 때만** 내린다.
- 코드에서는 `Claimed<T>`와 `Verified<T>`를 다른 타입으로 두고, `Verified<T>`는 재파생 검사를 통과한 함수만 만들 수 있게 한다. 화면과 서명은 `Verified<T>`만 받는다.

## 4. 검증기

**공격으로 판정 (빨간 화면, 서명 불가)**

| 상황 | 근거 |
|---|---|
| 입력·출력이 이 시드의 지문을 주장하지만 그 경로의 키가 시드에서 나오지 않음 | SS, CC, PP |
| 출력이 이 시드의 키를 주장하지만 실제 스크립트에는 다른 키 (또는 그 반대) | SS (Output Ownership Contradiction) |
| 입력이 이 시드의 키를 주장하지만 커밋된 스크립트가 그 키를 쓰지 않음 | SS |
| 입력이 제공한 redeem/witness 스크립트가 scriptPubKey의 커밋과 다름 | SS |
| 이전 거래의 txid가 입력이 가리키는 것과 다름, witness_utxo가 이전 거래와 모순 | SS, KS, PP |
| 전역 xpub이 이 시드의 지문을 주장하지만 마스터 키에서 파생되지 않음 | PP |
| 거스름 경로 구조 위반: 입력과 다른 계정·스크립트 종류, 분기가 0/1이 아님, 강화 인덱스, 너무 짧은 경로 | SS |
| 같은 UTXO가 이번 전원 세션에서 서명했을 때와 다른 금액으로 옴 | CC |
| 승인 후 서명 직전 재계산 결과가 승인 때와 다름 | CC, Trezor |

**형식 오류 (서명 불가)**: UTXO 정보 누락 · 레거시 입력에 이전 거래 없음 · 필요한 스크립트 누락 · 불필요한 스크립트 · 음수 수수료 · 중복 입력 · 이 시드로 서명할 입력이 없음 (지문 need/found 표시) · 이미 모두 서명됨 · 비표준 SIGHASH · 잘못된 OP_RETURN · 네트워크 불일치 · 탭루트 스크립트 경로만 가능 · 지원하지 않는 입력 · BIP-174 구조 위반(중복 키, 길이 오류)

**확인이 필요한 상황 (노란 화면)**

| 상황 | 동작 |
|---|---|
| 입력이 2개 이상인 segwit v0 거래에 이전 거래가 없음 (금액 검증 불가, CVE-2020-14199) | **"입력 금액을 확인할 수 없음"** 화면. 기본은 진행 불가, 사용자가 "이번 거래만 검증 없이 진행"을 고를 때만 계속 (결정 1) |
| 수수료 과다 | 결정 2 |
| 거스름 주소 번호가 입력보다 10,000 이상 큼 | 경고 (SS) |
| 거스름 없음 (전액 지출) | 경고 (SS) |
| 입력 스크립트 종류가 섞임 / 여러 계정의 입력 | 경고 (JD, SP) |
| 이 시드 것이 아닌 외부 입력 (페이조인 등) | 경고 + 수수료 계산 불가 표시 (CC) |
| 일부 입력이 이미 서명됨 | 경고 (CC) |
| OP_RETURN 여러 개 또는 80바이트 초과, 알 수 없는 스크립트 출력, 0원 출력 | 경고 (CC) |
| 기본이 아닌 locktime, RBF | 정보 표시 (Trezor) |

## 5. 서명

| 단계 | 내용 |
|---|---|
| 1. 서명 직전 재검증 | 승인 화면에 썼던 판정(내 입력·거스름·금액·수수료)을 처음부터 다시 계산해 같은지 확인 (CC, Trezor) |
| 2. 키 파생 | 입력마다 검증된 경로로 개인키를 파생하고, 그 공개키가 PSBT의 키·UTXO 스크립트와 같은지 다시 확인 |
| 3. 서명 해시 | 레거시 / BIP-143 / BIP-341 (탭루트는 모든 입력의 금액·스크립트 커밋) |
| 4. 서명 | ECDSA: RFC 6979 nonce, low-S, **low-R 그라인딩**. Schnorr: BIP-340, 탭루트 키 트윅, 보조 난수 0(결정 4) |
| 5. 서명 검증 | 만든 서명을 공개키로 직접 검증. 실패하면 그 PSBT 전체를 버리고 오류 화면 (오류 주입·버그 대비) |
| 6. 소거 | 개인키·nonce·중간 버퍼를 즉시 소거 |
| 7. 결과 | 서명만 남긴 축소본 (결정 3). 서명 수가 실제로 늘었는지 확인 (SS) |
| 8. 기억 | 서명한 segwit UTXO의 (txid:vout, 금액)을 전원이 켜져 있는 동안 기억 (CC) |

암호 구현: mod n 곱셈·역원(상수 시간) 추가, 비밀 값 연산은 M2처럼 타이밍 측정.

## 6. 화면

1. **PSBT 수신**: 지문으로 맞는 시드를 자동 선택. 없으면 "이 거래가 찾는 시드: 73c5da0a / 로드된 시드: …" (PP의 need/found).
2. **검증 결과**: 공격(빨강)·형식 오류는 여기서 끝. 확인이 필요한 상황은 하나씩 확인.
3. **개요**: SeedSigner식 금액 흐름. 입력 합계 → 받는 사람 n명 / 거스름 / 수수료.
4. **받는 사람**: 한 명씩 주소(4글자 묶음)와 금액. 내 다른 주소로 가는 출력은 "자기 송금" 표시.
5. **거스름**: 주소·경로·"이 시드의 주소로 확인됨".
6. **수수료**: 금액, sat/vB, 총 출력 대비 비율.
7. **최종 승인**: 요약 + "서명" / "취소", **기본 선택은 "취소"**. 모든 화면을 거쳐야 이 화면이 나온다.
8. **서명된 PSBT QR**: M3 표시 엔진 (낮은 밀도·느린 속도로 시작).

금액 단위는 설정(BTC / sats)을 따른다.

## 7. 테스트

| 대상 | 방법 |
|---|---|
| ECDSA | RFC 6979 벡터, libsecp256k1 `sign_ecdsa_low_r`와 **바이트 일치** (무작위 수천 건), Wycheproof (검증), 타이밍 측정 |
| Schnorr | BIP-340 공식 벡터, libsecp256k1과 같은 보조 난수에서 바이트 일치 |
| 서명 해시 | BIP-143 예제, BIP-341 지갑 테스트 벡터, Bitcoin Core `sighash.json` |
| PSBT | BIP-174·371 유효/무효 벡터. rust-bitcoin(테스트 전용)으로 4종 지갑 PSBT를 만들어, 우리 서명을 rust-bitcoin의 독립 서명 해시로 검증 |
| 공격 시나리오 | SeedSigner 시험 125개(MIT)의 상황을 Rust 시험으로 옮겨 같은 판정인지 확인. Coldcard 시험 PSBT 37개는 내려받아 시험 (저장소에 넣지 않음) |
| 화면 | 상황마다 PSBT를 만들어 화면 흐름 확인 (공격·오류는 서명 화면에 도달할 수 없어야 함) |
| 퍼징 | PSBT·거래 파서, 검증기 |
| 실제 | Signet에서 Sparrow 송금 |

## 8. 커밋 단위

1. 스칼라 곱셈·역원 + ECDSA (RFC 6979, low-S, low-R, DER) + 검증
2. Schnorr (BIP-340) + 탭루트 트윅 + 타이밍 측정
3. 거래 파서·직렬화·txid + 서명 해시 3종
4. PSBT 파서·직렬화 (BIP-174 / 371, 엄격한 구조 검사)
5. 검증기 1: 입력 무결성(금액·이전 거래·스크립트), 소유권(`Verified<T>`), 전역 xpub
6. 검증기 2: 출력·거스름 규칙, 수수료, SIGHASH, 공격/오류/경고 분류, UTXO 금액 기억
7. 서명: 재검증 → 파생 → 서명 → 서명 검증 → 소거 → 축소본
8. 검토·승인 화면, 오류·공격 화면, 최종 승인
9. 서명 결과 QR + 시뮬레이터 + 공격 시나리오 시험 + 퍼징 + 문서·배포

## 9. 완료 기준

- [ ] Signet: Sparrow 송금 PSBT를 시뮬레이터로 읽고, 검토·서명한 QR을 Sparrow가 읽어 방송까지 성공 — **사용자 확인 대기** (11장 끝의 방법)
- [x] 4종 스크립트 서명이 rust-bitcoin 독립 검증 통과, ECDSA는 libsecp256k1과 바이트 일치
- [x] SeedSigner 공격 시나리오에서 같은 판정 (다른 점 3가지는 11장), 공격·오류 상황은 서명 화면에 도달하지 못함
- [x] 퍼징 패닉 0건, CI 전부 통과

## 10. 결정 필요

1. **segwit v0 입력에 이전 거래가 없을 때 (입력 2개 이상)**
   - **(권장)** 차단 화면 → 사용자가 "이번 거래만 검증 없이 진행"을 명시적으로 고를 때만 계속 + UTXO 금액 기억 (Passport + Coldcard)
   - 무조건 차단 (Trezor) — 가장 안전하지만 이전 거래를 넣지 않는 지갑과는 서명 불가
   - 경고만 (Krux)
2. **수수료**
   - **(권장)** 총 출력의 5% 이상 경고, **10% 이상 기본 차단** (Coldcard 기본값, 차단선은 M6 설정에서 조정), 1,000 sat/vB 초과 경고
   - 25% 이상 강한 경고, 차단 없음 (SeedSigner·Passport)
3. **서명된 PSBT 출력**: **(권장)** 서명만 남긴 축소본 / 전체 PSBT
4. **Schnorr 보조 난수**: **(권장)** 0 (결정적, Jade와 같음) / 하드웨어 TRNG 섞기 (H 트랙 이후)
5. **결과 QR 형식**: **(권장)** UR 기본 + BBQr·Specter 선택 / UR만

## 11. 구현 결과

| 항목 | 결과 |
|---|---|
| ECDSA | RFC 6979(libsecp256k1과 같은 시드 배치) + low-S + **low-R 그라인딩**: 무작위 1,500건이 libsecp256k1과 **바이트 일치**(일반·low-R·DER), Wycheproof `ecdsa_secp256k1_sha256_bitcoin` 464건, 엄격한 DER(BIP-66). 서명 시간은 키에 무관 (Welch t = 1.4, 역원 t = −1.0) |
| Schnorr | BIP-340 공식 벡터 19개, 같은 보조 난수에서 libsecp256k1과 바이트 일치 1,500건, 서명 직후 자체 검증. BIP-341 트윅: 지갑 벡터의 키 경로 서명 7개가 보조 난수 0에서 **그대로 일치**. 타이밍 t = 0.4 |
| 거래·서명 해시 | Bitcoin Core `sighash.json` 500건, BIP-143 예제 전부(해시 유형 6가지·OP_CODESEPARATOR), BIP-341 SigMsg·해시 7개, 무작위 거래 600개 × 모든 해시 유형을 rust-bitcoin과 비교 |
| PSBT 파서 | Bitcoin Core의 검사 전부 + rust-bitcoin이 더하는 검사 + 우리 규칙(혼성 키 금지, 입력·출력 없는 거래 거부). Core `rpc_psbt.json`(무효 87개 거부, 유효 48개), BIP-174·371 벡터, 변형 25,000개에서 rust-bitcoin과 판정·필드 일치, 다시 쓰면 바이트 동일. PSBT v2는 "지원 안 함"(M7) |
| Coldcard PSBT 37개 | 내려받아 시험(저장소에 넣지 않음, MIT + Commons Clause). 오류 파일 7개 모두 거부(이유 고정), 나머지 30개 통과·rust-bitcoin과 txid 일치, 위조 witness 스크립트는 "공격" |
| 검증기 | `Claimed<T>`/`Verified<T>` 타입 분리(검증 값은 재파생 함수만 생성). 공격 9종·오류 24종·경고 13종 (화면 문구 46개). 계정 xpub만 캐시(개인키는 강화 경로를 파생하는 동안만 존재) |
| SeedSigner 시나리오 | 단일 서명에 해당하는 약 60개 시험의 상황을 25개 Rust 시험으로 재구성(코드·데이터 복사 없음), 같은 판정 |
| 서명 | 승인 판정의 해시를 서명 직전에 다시 계산해 비교, 검증된 경로로 키 파생 후 공개키 재확인, 모든 서명 검증(탭루트는 UTXO의 출력 키로), 축소본을 다시 파싱해 서명 수·키 확인, 실패하면 출력 버퍼 소거. 서명한 UTXO 금액을 전원이 꺼질 때까지 기억 |
| 독립 검증 | 4종 스크립트·다중 입력·혼합 입력 서명을 rust-bitcoin의 서명 해시로 검증하고 libsecp256k1 서명과 바이트 비교, 크기 추정 ≥ 실제 크기(입력당 1바이트 이내). BIP-174 서명자 벡터 4개와 Core 서명자 사례를 우리 해시·ECDSA로 재현 |
| 화면 | 시드 자동 선택(need/found), 공격·오류 화면(승인 화면에 도달 불가), 경고 하나씩 확인, "이번 거래만 검증 없이 서명"(기본 취소), 개요·출력별(주소 4글자 묶음, 거스름은 경로와 "확인됨")·수수료(sat/vB, 비율, 크기, locktime, RBF), 최종 승인(기본 취소) |

| 시뮬레이터 | 서명된 PSBT를 base64 텍스트로도 제공(웹캠 없는 지갑용), 붙여넣기 48 KB. 헤드리스 Chromium으로 시드 불러오기 → PSBT 붙여넣기 → 검토 → 서명 → UR QR까지 확인 |

### 계획과 달라진 점

| 계획 | 실제 | 이유 |
|---|---|---|
| SeedSigner와 같은 판정 | 같은 판정 + SeedSigner에서 가져온 더 엄격한 규칙 5가지(짧은 경로, 단일키 출력의 여분 파생 정보, 맵 종류 모순, 남의 지문으로 표시한 우리 출력, 이전 거래 없는 다른 기본 경로의 segwit v0 입력은 해제 불가) | 시나리오를 옮기면서 발견 |
| — | 다른 점 3가지: 다른 계정으로 보내는 출력은 "자기 송금"으로 표시(SeedSigner는 송금), 스크립트 트리가 있는 탭루트 키 경로는 M7까지 거부(SeedSigner는 서명), 멀티시그 시나리오는 M7 | 보수적 선택 |
| 거스름 번호 경고: 입력보다 10,000 이상 | 같은 기본 경로 입력 중 **가장 작은** 비강화 번호부터 10,000 (SeedSigner와 같게) | 시나리오 일치 |
| — | rust-bitcoin보다 느슨했던 곳(x-only 키 유효성, 해시 원상, 제어 블록, xpub 버전)을 rust-bitcoin 수준으로 | 변형 시험에서 발견 |
| — | BIP-174 서명자 벡터는 low-R 그라인딩 이전에 만들어져(r 상위 비트 1) 그라인딩 없는 RFC 6979와 비교 | 벡터의 서명 형태 |

### Signet 실송금 확인 방법

1. Sparrow를 Signet으로 실행하고, 시뮬레이터에서 만든(주사위·동전) 시험용 시드의 xpub QR을 Sparrow로 가져와 감시 지갑을 만든다 (Settings > Network = Signet).
2. Signet 수도꼭지에서 받은 코인으로 Sparrow에서 송금 PSBT를 만들고 QR(UR)로 보여 준다.
3. 시뮬레이터: 같은 시드를 불러온 뒤 메인 메뉴 1(Scan QR)에서 웹캠으로 읽거나, PSBT를 base64로 붙여넣는다.
4. 검토 화면을 모두 거쳐 서명 → UR QR을 Sparrow의 웹캠으로 읽거나, 시뮬레이터 아래의 "Signed PSBT" 텍스트를 Sparrow에 붙여넣는다.
5. Sparrow에서 Finalize → Broadcast.
